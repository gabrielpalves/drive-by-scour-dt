## 1. Classifier / sensors

**1.1 Champion = 2 sensors: RearBogie_Vert + CarBody_Pitch (DOF 2,5), PAA + N-HiTS, 61-class.** — *built*
Why: in the 540-run ablation this is the best 2-sensor pair (median MSE 0.414 ≈ full-8-DOF 0.386) and, unlike the alternative CarBody_Pitch + FrontBogie_Pitch, **both** of its single-sensor fall-backs are usable (CarBody_Pitch is the best single channel; FrontBogie_Pitch *alone* collapses 62% of the time). Sensor economy ("2 ≈ 8") is the headline of Paper 1.
Ref: our ablation (`ablation_analysis/summary_per_config.csv`). Sensor-economy framing aligns with drive-by SHM literature (Fernandes et al. 2024–2026).

**1.2 Observations sampled from a held-out MATLAB library, not live re-simulation.** — *built*
Why: one live TTBI passage is slow, and (historically) live Python re-sim mispredicted. Sampling a held-out set generated by the *training* pipeline removes train/serve skew and makes a fine monthly clock cheap (cf. Torzoni's pre-computed `recordings_*.npy`).
Status note (skew investigation, 2026-06-15): live Python re-sim **still** mispredicts — healthy is fine (0%→1%) but every damaged state is read as ~healthy (20/40/55% → 0–1%). Ruled out: the 13-vs-61-class metadata bug (fixed); the damage interface (Python's legacy `DOF_ChangeRate_value` maps to `scour_rates[n//2]` = central pier, same as MATLAB `A00`); and the **rail profile** (Python `TTBI_2D/x.mat`/`h.mat` are byte-identical to the MATLAB training profile `scour_MATLAB/Calc.ProfileData15_05.mat` — both pipelines use ONE fixed profile via `Profile.Type=2`). Remaining cause is in the **physics/geometry port**; prime suspect = the geometry constants forced in `b19_generate_profile.py`'s Type-2 debug block (`L=325.80`, approach `30/30`, `L_bridge=39.90`) vs `a04_options.py`'s `minL_Approach=16/minL_After=10`, which can misalign the (correct) profile against the simulation's actual track positions. Decisive next test (not yet run): compare a Python vs MATLAB signal at the same damage. **Practical decision:** generate the probe (and any DT observation) via MATLAB — it inherently uses the training pipeline. Repairing live Python is an optional, separable follow-up.

**Side-finding (record for the paper):** training AND the held-out set use a SINGLE FIXED rail profile (`Calc.ProfileData15_05.mat`, MATLAB `Profile.Type=2`). So rail-profile irregularity is NOT a source of operational variability in our data (only speed, temperature, vehicle properties, and signal noise are). Consistent (champion trained and served on the same profile), but a documented scope limit; rail-profile *as a damage type* (`profile_intensity`) is a separate, deliberate toggle.

## 2. Deterioration (scour)

**2.1 Scour = Kamariotis gradual power-law + Compound-Poisson flood shocks.** — *built*
Why: scour is flood-driven; a gradual creep plus discrete flood jumps is the accepted phenomenology.
Ref: Kamariotis et al. (2024), *Quantifying the value of SHM*.

**2.2 Multi-foundation correlation via a Gaussian copula** (river common factor + proximity term). — *built, optional*
Ref: Adnan (2026) for the foundation-proximity correlation term.

## 3. Cost / decision

**3.1 Monetary cost model with verified € figures** (c_failure 5e7, c_inspect 2e4, c_repair 6e5, downtime 1.5e5/day, 2% discount). — *built*
Ref: Kamariotis et al. (2024).
Flood-branch actions added 2026-06-24 (placeholders, set from project data): `restrict_operations` ≈ **3e3 €** (a couple of slow/light probe passages = a small reduced-capacity penalty, far below an inspection so the cheap probe has a real niche) and `interrupt` ≈ **3.2e5 €** (= inspection + ~2-day precautionary closure). Ordering do_nothing(0) < restrict(3e3) < inspect(2e4) < interrupt(3.2e5) < repair(5.1e6), so the flood planner escalates only as the risk warrants.

**3.2 Failure = a LOGNORMAL fragility P(fail | scour) = Φ((ln s − ln θ)/β), reported as a SWEPT assumption.** — *built 2026-06-15* (`costs.py::failure_prob` now lognormal; `calibrate.py::fragility_sensitivity` sweeps median θ × dispersion β; validated: P(0)=0, P(θ)=0.5, brittle β=0.05 near-step vs ductile β=0.4 gradual; cost-optimal repair threshold moves sensibly — brittle repairs later, ductile earlier)
Why: the scour literature uses a **lognormal** fragility CDF (not logistic) — justified by non-negativity of scour and multiplicative uncertainty. IM = scour intensity (our % stiffness loss, or relative scour depth Y = scour/foundation depth); θ = median capacity (50% failure point); β = lognormal dispersion. The planner ranking is not robust to the curve, so we **sweep** θ and β rather than commit to one. TTBI never models collapse — failure is a separate layer.
Literature parameters to bracket the sweep: masonry-arch (shallow, brittle) θ≈**1.52 m**, β≈**0.05** (near-step); deep piers β≈**0.3–0.4** (median geotech-dependent); counter-intuitively, piles in stiff clay can fail at *shallower* scour than in soft sand (loss of lateral confinement).
Refs: Maroni/Tubaldi/Douglas et al.; Lamb et al. (UK railway masonry); "A methodology to derive scour fragility functions for masonry arch bridges" (NSF/par.nsf.gov 10579270); "Flood-Induced Scour Fragility Analysis of Bridges in Different Soil Conditions" (E3S 2025); MCEER-03-0002 (lognormal fragility statistics). `digital_twin/calibrate.py::fragility_sensitivity`. **OPEN: implement the lognormal swap in `costs.py`; pick the swept θ/β range; decide whether IM = % stiffness loss or relative scour depth.**

**3.3 Planners: do_nothing / cost-VI (MDP) / heuristic (Kamariotis) / POMDP (myopic VoI) / hybrid.** — *built*
Why: a ladder from naive to information-aware; the POMDP is the only one that inspects rationally (inspection has purely informational value). Active inference is a planned upgrade (§5.3). A separate **`FloodResponsePlanner`** (§6.4) handles the major-flood branch for every routine planner, so "flood protocol ON vs OFF" isolates the value of flood-aware monitoring.

## 4. Risk perception

**4.1 Risk-sensitive objective via a coherent risk measure (CVaR / entropic), one aversion knob; default neutral = expectation.** — *built*
Why: a realistic asset owner is risk-averse to the catastrophic-failure tail; CVaR/entropic make that explicit and sweepable.
Ref: Chadha et al. (2023); Ames et al. (2025); Todd group (UCSD).
Finding (mock): with a cheap, sharp inspect available, risk-aversion buys **more monitoring** rather than fewer failures (the flood tail is largely irreducible by policy); without inspect, it repairs earlier. Robust across observation noise. **Figure 2026-06-24** (`plotting/risk_perception_figure.py` → `results/risk_perception/risk_perception.png`): sweeping CVaR_α from neutral to worst-5%, inspections per trajectory climb ~0.9 → 53 while **repairs stay flat (~0.1)** and **mean final damage is unchanged (~10.8%)**; the **CVaR_10 € tail rises** (10.8M → 12.9M) rather than shrinking. Mechanism: a cheap sharp inspection re-collapses the belief to a spike before the repair decision (CVaR≈mean on a spike), so risk routes into inspection; the catastrophic tail is dominated by sudden flood-shock jumps that outrun the inspect/repair loop. Cutting that tail needs faster monitoring or a shock-anticipating policy (→ the flood branch §6.4), not a more risk-averse objective.

## 5. Sensor health

**5.1 Three failure modes — transient burst / degraded / dead — with fault & noise scaling carbody < bogie < wheel.** — *built (placeholder rates)*
Why + ref: EN 61373 install categories give the physical basis and the vibration ratio. Functional RMS acceleration: **Cat 1 (car body) 1.01, Cat 2 (bogie) 5.40, Cat 3 (axle box) 38.0 m/s²** → wheel ≫ bogie ≫ car body, scaled by a vibration-fatigue acceleration law (Basquin/Steinberg, exponent ~6.4 for the S–N relation). Refs: EN 61373, EN 50155; Sandia *MEMS reliability in a vibration environment*; MDPI *Reliability of MEMS inertial devices…* (2024). See `papers/Confiabilidade MEMS Ferroviário.docx`.

**5.2 Degraded mode = persistent bias offset + scale-factor error + elevated noise** (not just noise). — *built*
Why: the dominant long-term MEMS failure is *parametric* (slow bias/scale-factor drift, VRE), not sudden death — the FMEDA "dangerous undetected" (λDU). VRE ≈ 0.5 °/h/g² (a 10 g bogie level → ~50 °/h bias). Time-to-parametric-failure (25 °/h bias) ≈ 1588 d at 25 °C → 558 d at 60 °C, i.e. car body ≫ bogie/axle lifespan. Arrhenius Ea ≈ 0.8–1.0 eV (general CMOS) / 0.16–0.22 eV (bias drift); infant mortality 0.3–5%; intermittent connector ≈ 200–500 FIT (Cat 3).
Caveat recorded in code: per-channel standardisation in our preprocessor largely removes a constant bias/scale, so for our PAA pipeline the *noise* term dominates the classifier impact; bias/scale are kept for raw-signal re-users and physical fidelity.
Refs: as 5.1 + MDPI *Reliability Assessment of MEMS Gyroscopes via Dual-Mechanism Synergistic Degradation (Physics-Informed Wiener Processes)* (2024); Tronics AXO305 / GYPRO4300 & ADI ADIS16488 datasheets.

**5.3 Coping: dead → fall back to the surviving single-DOF champion (and its wider confusion matrix, so the belief distrusts it); cheap inspect/replace-sensor actions.** — *built*
CONFIRMED (Step 1): **(b) dead-detected / degraded-undetected** — a dead sensor is obvious (flat/zero) → fall back; a degraded one is the λDU case (looks plausible, silently corrupts the estimate). The 2-sensor cross-check that catches some degraded cases is a later step toward full diagnosis (c).

## 6. Monitoring cadence & floods

**6.1 ~30 instrumented passages per month (default).** — *decided (build pending)*
Why: drive-by SHM counts only the *instrumented* train's crossings. A daily in-service passenger train ⇒ ~30/month; 60 is also realistic but heavier to simulate and makes no qualitative difference. We define the problem, so 30 is the chosen default.

**6.2 Routine vs flood regimes differ.** — *decided (build pending)*
Routine month: ~30 passages → (a) fuse for a near-certain monthly state, (b) sensor self-diagnosis. Flood month: few, risky, possibly-corrupted reads. ⇒ value of risk-awareness + sensor-health concentrates at floods.

**6.3 Major vs minor floods — JUSTIFIED.** — *decided*
Major flood = a hydrologically significant event, **observed externally via a river-stage gauge** → triggers the decision branch. Minor flood = small jump, **not signalled**; revealed only through subsequent routine drive-by data. We act only on observed major floods.
Literature basis (defensible for a structural-engineering paper): FHWA **HEC-18** and **AREMA Ch.8** define the **100-year design flood** (1% AEP) and **500-year check flood** (0.2% AEP); "erosion-critical" bridges carry a legally-required **Plan of Action** with **gauge-linked triggers** for inspection/closure — exactly our decision branch. Observation: river **stage** is measured precisely (±0.2%) by radar/pressure/acoustic sensors; **discharge** is inferred via a stage-discharge rating curve. Multi-source fusion (structural drive-by + hazard gauge) updated by a Bayesian Network is the state of the art (Maroni et al.; Kamariotis VoI). An advanced option is Maroni's **adaptive threshold**: solve the inverse-reliability problem for the stage that exceeds a target P_f given the SHM-updated capacity (vs a static 100-yr stage). Refs: FHWA HEC-18 (hif12003); AREMA Ch.8; Maroni et al. (Bayesian DSS, adaptive thresholds, Strathclyde/Heriot-Watt); Lamb et al. (Britain's railway scour economic risk).

**6.3b Flood-observation uncertainty → probabilistic classification.** — *built 2026-06-24* (`digital_twin/flood.py::FloodTrigger`)
Critically, the trigger is uncertain: discharge error is 2–6% in ideal flow but **50–200% when the rating curve extrapolates during the extreme floods that matter** (plus hysteresis/loop-rating). So "is this a major flood?" is itself noisy. **Implemented** as `P(classify major | severity) = Φ((ln s − ln s_major)/β_gauge)` — a lognormal CDF on a dimensionless severity `s` = (flood scour jump)/(mean jump). Construction (the clean story for the talk): the operator declares major when the gauge-inferred discharge crosses the design-flood threshold `s_major`; because the discharge inference is uncertain the gauge reads `gauge = s · ε` with ε lognormal of dispersion `β_gauge` (median-unbiased — the rating curve is the median relation), and marginalising the **hard threshold over the gauge noise gives the smooth CDF**. `β_gauge → 0` recovers the deterministic design-flood threshold; `β_gauge ≈ 0.6` is the default (50–200% extreme-flood rating error). Verified: `classify(observe_gauge(s))` reproduces `p_major(s)` in expectation. Figure: `plotting/flood_decision_map.py` → `flood_trigger_cdf.png`. To be refined with the Todd group; `s_major` and `β_gauge` are swept knobs.

**6.4 Major-flood decision branch.** — *built 2026-06-24* (`digital_twin/planner.py::FloodResponsePlanner`, integrated in `simulation.py::DTSimulator._major_flood_step`)
On an observed major flood the belief is **widened** by the uncertain scour shock (`flood.py::widen_belief`: a severity-scaled upward-diffusion kernel — the median label jump ≈ severity × mean jump, with dispersion folding in the gauge + jump uncertainty), then the owner chooses among **do_nothing / restrict_operations(probe) / inspect / interrupt** by a **risk-adjusted one-step Value-of-Information** rule (the same logic as the POMDP, generalised to several information actions with different cost, observation model, and protection):
`J(a) = action€ + expo·R(b) + E_obs[ commit(posterior) ]`, where `R(b)` is the risk-perceived failure cost carried by the (open) line, `commit(b)=min(R(b), c_repair)`, and the `expo·R(b)` exposure term (the failure risk an OPEN line carries while the survey result is pending, ≈ inspection-latency/step) **cancels among the three open actions but is removed by `interrupt`** — so closure is chosen precisely when `R(widened)` is large (near-threshold belief × severe flood). The probe carries a `reliability` factor (probability it yields usable data); a low value collapses its VoI → the planner escalates to inspect/interrupt (the **sensor-corruption escalation, at the decision level**), and the simulator also escalates a *realised* corrupted probe (`_probe_update` returns 0 usable passages → inspect). Restricted-ops fuses `n_probe` passages (multi-passage flood read). Risk aversion (RiskModel) up-weights the widened tail, lowering the bar for inspect/interrupt. The resulting four-region **decision map** (severity × pre-flood belief) and its shift under risk aversion / degraded sensors is `flood_decision_map.png`. **Finding (decision composition):** in the realistic regime (rare, already-severe major floods on a low pre-flood belief) the response is almost always **inspect**, with **interrupt** in the severe corner and the cheap **probe** occupying only a thin "barely-major + nearly-healthy" band — i.e. once a major flood is *declared*, doing nothing is rarely optimal.
**Finding (€ value, `plotting/flood_value_figure.py` → `results/flood_value/`):** because routine monthly drive-by already catches the post-flood scour at the next passage, the flood branch's effect on the *mean* life-cycle cost is small (a one-month head start + targeted closures). Its value is in the **catastrophic tail**: it trims the CVaR_10 cost by ~2% (POMDP/Hybrid, base fragility) up to **~6% under a conservative fragility** (θ=0.4, where flood-shock scour actually threatens failure). This is precisely the flood-shock tail the risk-perception result (§4.1) showed risk-aversion *cannot* reach — so the flood-ANTICIPATING protocol is the policy that addresses it (a small mean premium for tail insurance). The value grows further when routine monitoring is sparse/unreliable (untested lever). Fragility is swept throughout.

**6.5 Restrict-ops probe = a WIDER observation model; measured later, assumed now.** — *built 2026-06-24 (assumed); MATLAB measurement deferred*
The probe (low mass, locked low speed) is a *different operating condition* than the held-out library, so its confusion matrix should be **measured** from a matching MATLAB batch. Until that batch exists the probe uses an **assumed** wider banded matrix (`probe_sigma ≈ 1.0`, vs drive-by `≈ 0.7`); the harness already loads a **measured** matrix from `probe_dir` when supplied, so the real probe path is scaffolded (`run_comparison(..., probe_dir=...)`). `probe_corruption_prob` injects realised per-passage probe loss for the mock escalation demo. (Live Python re-sim now matches MATLAB, so the probe could alternatively be generated live — see the skew-fix note in §7.)
